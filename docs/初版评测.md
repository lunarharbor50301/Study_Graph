# StudyGraph 初版评测方案

版本：v0.1（讨论稿）  
日期：2026-11-10  
状态：评测设计，尚未运行实验；本文不包含实测结果。

## 1. 目标与范围

验证 StudyGraph 能否围绕课程讲义正确组织知识、提供可追溯解释、定位学生错误并给出针对性提示，同时完成概念导航与作答重试流程。

本方案依据《StudyGraph_Project_Proposal.pdf》第 2 页 Evaluation Plan。Proposal 要求固定测试集离线评测，覆盖知识抽取、引用、导航、反馈与效率，并与相同模型和检索组件的直接回答 baseline 比较。本文的题量、分值和执行细则是建议方案，需要团队确认。

第一轮使用一份讲义中的局部内容验证评测方法；最终仍需扩展至 proposal 计划的同一课程 2–3 份讲义。离线结果支持系统可靠性和反馈质量结论，不直接证明真实学生的学习效果。

## 2. 所选 PPT 内容概况

来源：`lecture_sample.pdf`，Lecture 1: Processor Evolution — From CPU to GPU，共 67 页。下文均使用从 1 开始的 PDF 物理页码。

核心范围：p.37、p.40–46。

- p.37：block、warp、thread 的组织关系与 SIMT。一个 NVIDIA warp 包含 32 个线程；页面中的资源容量上限是 Fermi 示例，不作为通用 GPU 规格。
- p.40–41：warp 执行及交错调度，通过调度其他就绪 warp 隐藏等待延迟。
- p.42–43：CUDA core、SM 等术语以及 CPU/GPU 的执行组织对比，作为背景。
- p.44–45：同一 warp 内线程进入不同路径造成分支发散，降低活跃执行通道比例。
- p.46：通过组织线程与数据映射，让同一 warp 内线程走相同路径，减少发散。

内容链条：线程组织 → warp 执行 → 延迟隐藏 → 分支发散 → 利用率损失 → 工作重排。

暂不纳入正式评分：p.48 归约示例代码存在边界和循环问题。后续扩展至 p.47–48 前，应先修正代码并由另一名成员复核。

## 3. 研究问题

1. 系统能否覆盖核心概念，并建立正确、可追溯的概念关系？
2. 回答是否正确，引用是否真正支持回答中的关键主张？
3. 相比 baseline，StudyGraph 是否更准确地定位错误并提供相关提示？
4. 多轮交互是否维持概念上下文，并正确完成跳页、提示与重答？
5. 上述能力带来多少响应时间和调用开销？

## 4. Baseline 与 StudyGraph

### 4.1 共同条件

使用同一 TACC 模型及版本、同一讲义、解析结果、检索组件及配置；使用相同题目、学生答案、对话历史和任务要求。生成参数、检索数量、上下文限制和总输出预算固定并记录。

对于诊断与提示比较，两者都明确收到“判断答案、指出具体错误、给出提示并引用讲义”的任务。不能通过禁止 baseline 提示或只要求它回答对错来削弱 baseline。

评分者使用的完整人工答案与评分依据独立保存，不作为普通检索语料。若某些题目评分规则作为 StudyGraph 的功能输入，必须在实验配置中列明。

### 4.2 Baseline：检索后直接生成

输入问题、学生答案及对话历史 → 检索讲义 → 模型直接生成回答或反馈及引用。

不显式提供概念图、不加入结构化错因诊断和提示选择流程。模型可能自行给出高质量诊断，按实际输出评分。

### 4.3 StudyGraph：概念关联与针对性反馈

输入问题、学生答案及对话历史 → 检索并关联概念 → 根据题目评分依据定位错误 → 选择提示或解释 → 返回引用 → 保存作答、提示及重试记录。

这是待实现、待验证的目标流程，不代表当前仓库已具备全部能力。正式测试前必须记录实际启用的模块。

### 4.4 比较结论的边界

主实验比较整套系统方案。若 StudyGraph 额外使用题目评分依据、概念关系和反馈流程，提升不能单独归因于概念图。

可选消融：保留 StudyGraph 的评分依据、对话信息和反馈流程，仅移除概念关系输入，与完整版本比较。此项不作为第一轮必须完成的任务。

导航和记录功能单独验收；不因 baseline 没有图谱界面就给其输出质量扣分。

## 5. 固定测试集

第一轮建议规模：

- 6–8 个核心概念、8–10 条人工核对的显式关系。
- 8 道练习：5 道开发题、3 道保留题。
- 每题 2 份典型错答及 1 份正确答案：共 24 个作答反馈输入，避免只测错误答案而漏测误判。
- 6 道可由讲义回答的问答：4 道开发、2 道保留。
- 4 道讲义证据不足的问题：2 道开发、2 道保留。
- 4 条固定导航与多轮任务。

以上为试点规模建议，不替代 kickoff 中约 20 个概念、15 条关系、10 道练习和 20 份典型错答的后续总体目标。

### 5.1 数据划分

按题目及代码变式家族划分开发集与保留集。同一题的正确答案、错答、改写和近似变式进入同一个集合，避免泄漏。

开发集用于修改检索、提示词和流程；保留集在冻结版本后统一运行，不根据其结果继续调参后仍称为同一次最终测试。讲义本身可以用于检索，保留的是测试题及标注。

模型可辅助生成候选题，但参考答案、错误标签和来源页必须经人工核对。标记题目为讲义复用、人工自编或模型辅助。

### 5.2 每条样本的字段

`case_id`、`split`、`task_type`、`concept_ids`、`question`、`assumptions`、`reference_answer`、`required_points`、`student_answer`、`error_type`、`acceptable_hint`、`source_document`、`source_pages`、`source_chunk_ids`、`origin`、`reviewer`。

`source_chunk_ids` 待 B 完成解析后填入真实 ID；未绑定前使用页码，不伪造片段 ID。参考答案与提示允许同义表达，评分不采用简单字符串相等。

## 6. 开发样例

以下全部属于开发样例，不再作为最终保留题。

### D01：延迟隐藏与分支发散

- 问题：增加线程数量能直接消除同一 warp 内的分支发散吗？解释原因。
- 来源：p.37、p.41、p.44–45。
- 必要得分点：不能直接消除；发散涉及同一 warp 内的不同路径；其他就绪 warp 有助于隐藏等待，但不直接改变原 warp 的路径分布。
- 典型错答 A：能，线程足够多就会同时执行所有分支。
- 错因 A：混淆跨 warp 延迟隐藏与 warp 内通道利用率。
- 典型错答 B：不能，因为 GPU 一次只能运行一个线程。
- 错因 B：结论正确但执行模型错误，不能判为完全正确。
- 第一层提示：先只看一个 warp，执行某条路径时，走另一条路径的线程是否在做有效工作？
- 更强提示：调度另一个 warp，与改变当前 warp 内线程的分支选择，是同一件事吗？

### D02：代码中的分支组织

- 条件：一维 block，共 64 个线程；warp 按连续线程索引划分；两个分支均包含实际工作。只比较分支组织，不推断整体程序语义等价或精确耗时。
- 问题：比较条件 `threadIdx.x % 2 == 0` 与 `threadIdx.x < 32` 对 warp 内发散的影响。
- 来源：p.37、p.44–46；本题是基于讲义的自编变式。
- 必要得分点：前者每个 warp 内存在两条路径；后者每个 warp 内条件一致，两个 warp 可以分别执行不同路径；不同 warp 的路径不同不等于 warp 内发散。
- 典型错答：两者都有 if，所以发散相同。
- 提示：分别列出线程 0–31 和 32–63 的条件真假。
- 不应给满分的结论：后者必然快两倍。讲义不足以给出这样的固定加速比。

## 7. 评分角度与指标

### 7.1 知识抽取与图谱

- 概念覆盖率 = 正确覆盖的参考概念数 / 参考概念总数。
- 关系正确率 = 判定正确的生成关系数 / 被审核的生成关系总数。
- 关系覆盖率 = 正确覆盖的参考关系数 / 参考关系总数。
- 检查方向、类型、证据及推断标记。正确但不在参考集合中的关系单独核对，不直接认定为错误；推断关系不冒充讲义明示关系。

### 7.2 答案与引用

- 答案正确性：0=主要结论错误；1=部分正确但缺必要推理或有实质遗漏；2=必要得分点齐全且无实质错误。
- 引用有效率：文档、页码、片段均可解析的引用数 / 所有输出引用数。
- 引用支持率：确实支持关联主张的引用数 / 被审核引用数。
- 关键主张证据覆盖率：有支持性引用的关键主张数 / 需证据的关键主张数。避免“只引用一句容易证明的话”获得虚高分数。
- 证据不足识别率：在超范围问题上明确说明讲义证据不足的样本数 / 超范围样本总数。同时记录对可回答问题的不必要拒答。

自动检查引用是否存在；人工检查它是否支持语义。没有引用时引用比例记为不适用，不能计作 100%；通过证据覆盖率体现缺失。

### 7.3 错误诊断

- 作答判定准确率：对正确、部分正确、错误的分类与人工标准一致的比例。
- 错因定位：0=错判或仅说“错误”；1=指出大方向但不具体；2=指出具体错误及其与正确概念的区别。
- 多错因样本提前标注主要错误和可接受替代标签，避免评分者事后改变标准。

### 7.4 提示质量

分别对以下四项给 0–2 分，保留分项结果：

1. 正确性：是否包含技术错误。
2. 针对性：是否回应该学生的具体误解。
3. 可行动性：是否给出明确的观察、计算或推理下一步。
4. 提示程度：在请求提示时是否适度保留推理空间；用户明确要完整解释时，不因提供答案而扣分。

0=不满足，1=部分满足，2=充分满足。正确性为 0 的反馈单独列为严重失败，不能用其他高分抵消。

### 7.5 导航与多轮任务

固定任务：选概念并提问；连续追问；从引用打开正确原页；请求练习、答错、提示、重答。

记录概念上下文对齐率、正确跳页次数/跳页尝试数、完整任务成功数/任务总数。重答验收须核对两条不同 attempt 记录、同一题目和会话关联，以及提示事件的保存。

固定脚本中的重答只验证流程和记录正确；其“答对”不能视为提示提升学习效果的证据。

### 7.6 效率

记录检索耗时、模型调用次数与总耗时、整体请求耗时、输入输出 token（若接口提供）、失败/超时。

汇总中位数、范围及原始值；小样本不强调不稳定的尾部百分位。固定超时设置，首次冷启动与预热后运行分开记录。StudyGraph 多次调用产生的额外时间必须计入整体耗时。

## 8. 执行与结果汇总

1. C 准备样本、评分标准和保留集；由另一名组员复核答案与出处。
2. B 固定模型、解析与检索配置；A 确认导航和学习记录接口。
3. 冻结代码 commit、提示词版本、数据划分及参数。先在开发集排除运行错误。
4. 两套系统逐样本配对运行；交替或随机化运行顺序，避免服务负载偏向一方。建议每个输入各运行 3 次，并保留全部结果。
5. 输出隐藏系统名称，随机编号；两名成员独立按同一标准评分，分歧讨论裁定并保留原分数。
6. 按同一 case_id 汇总两个系统的差值，报告各维度均值、原始样本量、失败数量与平局情况。
7. 重复运行不能当成新的独立题目。小规模试点以描述性结果为主，不凭少量样本宣称显著提升。
8. 至少分析一个 StudyGraph 不如 baseline 或两者都失败的例子，说明证据、错因及改进方向。

结果记录字段：`run_id`、`case_id`、`system`、`repeat_index`、`config_version`、`raw_output`、`retrieved_chunks`、`citations`、`scores`、`timing`、`error_status`、`rater_ids`。

## 切换 TACC / DeepSeek 运行评测

以下是当前代码的运行方式，历史报告中的模型名称和成绩保持原样；切换模型后应保存到新的结果目录并重新评分。[完整配置、参数和运行说明](../evaluation/runners/README.md)。命令均从仓库根目录执行。

先启动 TACC 模型及 SSH 隧道，然后在运行评测脚本的终端设置地址并检查接口：

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1

curl --noproxy '*' -fsS --max-time 8 \
  http://127.0.0.1:18024/v1/models
```

直接调用 TACC 的评测脚本不需要 DeepSeek API key。改用 DeepSeek 时，需要在当前进程配置 `DEEPSEEK_API_KEY`。如果密钥已保存在项目 `.env` 中，可以加载：

```bash
set -a
source .env
set +a
```

用 TACC 对已有概念图和笔记重新进行语义评分：

```bash
.venv/bin/python -m evaluation.runners.knowledge score --reference evaluation/01_knowledge/v0.5-en/lecture1.json --prediction evaluation/results/v0.5-en-20261119/l1/prediction.json --judge tacc --output evaluation/results/l1-tacc-metrics-new.json
```

换成 `--judge deepseek` 可切换裁判；此命令不会重新生成概念图。需要 TACC 生成时，在启动独立后端前设置 `STUDYGRAPH_GENERATION_PROVIDER=tacc`，再让 `knowledge generate --base-url` 指向该后端。不要把不匹配的参考集和历史预测拼在一起作公平对照。大体量裁判输入加16000输出token预算须适合TACC上下文窗口，超限不会自动截断或回退。
