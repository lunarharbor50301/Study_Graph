# 固定题目批改与反馈：第一轮开发测试

版本：v0.1，2026-11-10。状态：开发样例与接口建议，尚未运行模型评测。

## 1. 这次要测什么

固定题目和模拟学生答案，比较后端对答案的判断、错误定位、反馈和引用质量。测试暂时跳过 AI 出题：

固定题目 + 固定学生答案 → 后端批改与反馈 → 保存原始结果 → C 按标准评分。

这道题是公开开发题，可交给 B 反复调试，不再作为最终保留题。它放在独立测试文件中，不要求普通用户看到，也不要求写死在后端业务代码里。生产环境仍可以根据上传的 PPT 动态生成题目。

本次只覆盖一道题的六种答案，适合发现问题，不足以证明系统总体优于 baseline，更不能证明学生学习效果提升。

## 2. 固定题目

题目 ID：`warp-feedback-dev-01`。

题干：

> 在 NVIDIA CUDA 中，如果同一个 warp 内的线程进入不同分支，仅增加启动的线程数量，能否直接消除这个 warp 内的分支发散？请解释原因，并说明它与通过调度其他就绪 warp 隐藏延迟有什么区别。

条件：讨论普通 SIMT 分支发散；仅增加线程数量，不改变原 warp 内线程的数据分配、分支条件或代码。不要推断固定的性能加速倍数。

来源：`lecture_sample.pdf`，Lecture 1: Processor Evolution — From CPU to GPU。页码均为 PDF 物理页码，从 1 开始。

- p.37：warp、线程分组及 SIMT。
- p.41：交错执行其他 warp 以隐藏延迟。
- p.44–45：warp 内不同路径及利用率损失。
- p.46：改变工作组织以减少发散，作为辅助证据。

以上为阅读定位，不是已验证的检索片段 ID。B 解析后绑定实际 document_id、chunk_id。模型不得把示例 ID 当作真实引用。

## 3. 通用评分依据

参考答案：不能直接消除。原 warp 内线程仍然进入不同执行路径，执行某条路径时只有相应线程活跃。增加线程可能提供更多可调度 warp，使其他就绪 warp 在等待期间执行，从而帮助隐藏延迟；这不改变原 warp 的分支分布，也不保证性能提高。

必要得分点：

- K1：明确回答“不能直接消除”。
- K2：解释原 warp 内不同路径仍然存在，并造成部分线程/通道不活跃。
- K3：区分其他就绪 warp 的调度与原 warp 内路径组织；不得把更多线程等同于必然提高性能。

学生答案判定规则：

- `correct`：K1–K3 均满足，且无实质错误。
- `partially_correct`：有正确结论或关键机制，但缺重要解释，或夹杂错误理由。
- `incorrect`：核心结论错误，或整体机制解释与题目相反。

按含义判定，接受同义表达。不要用关键词命中代替理解。对于结论正确但理由错误的答案，需明确指出“结论正确、理由错误”。

## 4. 六份模拟学生答案

完整机器可读输入见 `../evaluation/archive/legacy/feedback_dev/inputs.json`；逐样本人工标准见 `gold.json`。

### A01：完整正确

“不能。原 warp 内线程的分支选择没有变化，执行一条路径时另一条路径上的线程不会做这条路径的有效工作。更多线程可能带来其他就绪 warp，以便在等待时切换执行，但不能消除原 warp 内的发散，也不保证性能一定提高。”

预期：correct。确认正确并简要解释，不应编造错因或强行给纠错提示。

### A02：正确的同义表达

“不会直接消除。问题出在这组线程走了不同路径，不在于总线程数少。别的线程组可以在当前组等待时接着干活，但原来那组执行某个分支时仍只有部分成员活跃。”

预期：correct。检验系统是否接受没有完整专业词汇但含义正确的答案。

### A03：结论对但解释不足

“不能，增加线程数不等于消除分支发散。”

预期：partially_correct。缺 K2、K3；应邀请补充机制，不应声称学生明确持有某个错误观念。

### A04：混淆延迟隐藏与发散

“能。线程足够多时，GPU 可以同时执行所有分支，把空闲资源填满，所以发散就消失了。”

预期：incorrect。具体错误是认为增加总线程数改变了原 warp 内分支情况，并保证资源填满。

可接受提示方向：先只看原来的一个 warp，增加其他线程后，它内部各线程的分支条件是否发生了变化？不要求照抄这句话。

### A05：结论对但执行模型错误

“不能，因为 GPU 一次只能执行一个线程，其他线程都必须等待。”

预期：partially_correct。K1 正确，理由错误。反馈需指出 GPU 可以并行执行多个线程，不能把该答案判为完全正确。

可接受提示方向：回到讲义中一个 warp 的线程组织，思考“只有一个线程执行”是否符合示意图。

### A06：混淆 warp 内与 warp 间

“能。只要不同 warp 分别走不同分支，同一个 warp 内原有的发散也会自动消失。”

预期：incorrect。没有改变原 warp 的工作分配，其他 warp 的路径不能自动改变它的内部发散。

可接受提示方向：分别描述“不同 warp 走不同路径”和“同一 warp 内走不同路径”，明确哪一种是题目中的情况。

## 5. B 怎么接入

当前仓库只实现了固定 Roofline 数值题 `/api/exercises/bw-01/attempts`，不能声称已经支持本题的开放式诊断。下面是建议的数据适配约定，不是现有可调用 API。

测试脚本读取题目和六条答案，每条答案独立调用实际的批改函数或接口。无需先上传到生产题库或修改页面；由 B 编写一个薄适配层，把固定题目传入与正常业务共用的反馈逻辑。

每次调用携带：

- exercise_id、题干、条件；
- 当前 student_answer；
- 独立 session_id（按系统、运行批次和样本区分）；
- mode=`hint_first`；
- 绑定后的真实 document_id。

不得把整份数据文件直接当作 prompt。每次只发送当前样本；case_id 仅用于日志，不提供含答案类型的标签。初轮六条输入彼此独立，不继承上一样本的聊天历史。

建议输出：verdict、已识别的具体问题、feedback、可选 hint、citations，以及原始模型文本。正确答案允许 hint 为 null；不确定或技术失败应显式记录，不能伪装成正常判分。

每条 citation 包含真实 document_id、chunk_id、page。由后端核验引用是否存在；C 核验原文是否支持对应主张。

## 6. 评审数据与运行数据的边界

- `inputs.json`：题目、条件、学生答案，可供测试适配层读取。
- `rubric.json`：通用题目评分依据，不包含某份学生答案的预期判定。
- `gold.json`：每条模拟答案的预期判定、错因和提示方向，仅供 C 评分；B 可人工查看开发样例理解需求，但运行时不可注入模型或检索库。

首轮为了检查批改功能，可以将相同 rubric 同时提供给两个配置，测试其他处理差异。若严格按 proposal 的直接回答 baseline 不提供 rubric，而 StudyGraph 提供，则需记录这一差异，结论只能归于整套方案。

两种实验口径不可混合汇总。正式执行前选定一种并记录：`shared_rubric` 或 `proposal_system_comparison`。第一轮建议使用 shared_rubric，减少误差来源。

不要给模型提供样本对应的 expected_verdict、error_type、人工期望提示或 C 的评分记录。

## 7. C 怎么评分

每份输出分项评分，不只看文字是否通顺：

1. 判定是否一致：对照 gold 的三分类，记 0/1。
2. 诊断准确性：0=误判或泛泛说错误；1=指出部分问题；2=准确定位主要错误或缺失。正确答案则看是否正确识别完整性且不捏造错误。
3. 反馈技术正确性：0=有实质错误；1=表述有重要歧义或遗漏；2=正确且无误导。
4. 下一步是否合适：0=无关或有害；1=泛泛提醒；2=针对错因提出可执行思考步骤。正确答案以适当确认和简要解释计分，无需强行出提示。
5. 引用有效性：逐条记录能否定位到真实原页/片段。
6. 引用支持性：逐条记录能否支撑关联解释；另记录关键解释是否缺少引用。没有引用不能算引用全对。

hint_first 模式下记录是否过早完整泄露答案。它不是“反馈越短越好”；目标是给足继续思考的依据。

保留各项分数、评语和原始输出。技术正确性为 0 单独列为严重失败，不用其他分数抵消。

## 8. 首轮执行步骤

1. B 将讲义接入解析与检索，确认相关页可读，填写真实文档绑定。
2. C 与另一名成员复核题目、参考答案及六份答案的判定。
3. B 冻结模型、检索、rubric 口径、prompt 和代码版本。
4. 先将六条答案各跑一次，保存结果，排除接口错误；这是开发测试，不是最终统计结论。
5. C 按第 7 节评分，指出“哪条输入、哪句话、违反哪个标准”。
6. B 选择一个明确问题改进；使用同样六条输入重跑，保留旧结果。
7. 若需要稳定性检查，每条各跑 3 次，记录全部运行；重复运行不是新的独立题目。
8. 后续新增其他题目的保留集，在版本冻结后评测泛化。

建议日志字段：run_id、case_id、system/config、模型及参数、代码 commit、prompt 版本、rubric_mode、检索片段、原始输出、结构化输出、引用、端到端耗时、失败状态。

baseline 与 StudyGraph 若尚未实现不同处理，先如实记录为 initial_backend。不要给相同实现贴两个标签再报告对比提升。

## 9. 交接与验收

C 提供本文和三个 JSON 文件；B 返回六条实际输出及日志；C 返回评分和优先失败案例。首轮验收是“测试能跑、结果可追溯、问题可定位”，不设未经测量的质量达标率。

本题属于开发数据，以后可以持续回归测试，但不得重新包装为从未见过的最终保留题。

## 切换 TACC / DeepSeek 运行评测

以下是当前代码的运行方式，历史报告中的模型名称和成绩保持原样；切换模型后应保存到新的结果目录并重新评分。[完整配置、参数和运行说明](../evaluation/runners/README.md)。命令均从仓库根目录执行。

先启动 TACC 模型及 SSH 隧道，然后在运行评测脚本的终端设置地址并检查接口：

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1

curl --noproxy '*' -fsS --max-time 8 \
  http://127.0.0.1:18024/v1/models
```

直接调用 TACC 的评测脚本不需要 DeepSeek API key。改用 DeepSeek 时，需要在当前进程配置 `DEEPSEEK_API_KEY`。如果密钥已保存在项目 `.env` 中，可以加载：

```bash
set -a
source .env
set +a
```

用 TACC 作为实验性学生答案批改模型，指标仍由代码对照参考标注计算：

```bash
.venv/bin/python -m evaluation.runners.grading_feedback --provider tacc --workers 1 --output-dir evaluation/results/grading-tacc-new
```

改成 `--provider deepseek` 即切回 DeepSeek。此参数不改变网页的答案规范化匹配规则；网页规则对照与模型批改仍分别报告。
