# StudyGraph 总体评测方案

版本：v0.1，2026-11-10。状态：设计稿，尚未开展正式实验，无实测结论。

本文按照项目 Proposal 第 3 节 Evaluation Plan 组织。Proposal 确定评测方向；本文的样本分配、评分细则和执行顺序是团队实施建议，正式运行前需冻结。

配套文档：[不同题型的判分与系统评测](不同题型的判分与系统评测.md)。将两个文件放在同一目录上传，即可通过相对链接互相阅读。本文不依赖其他开发样例文档。

## 1. 目标与评测边界

验证系统能否：

1. 从讲义组织正确、有出处的概念和关系。
2. 正确回答讲义问题，引用真正支持答案，并承认证据不足。
3. 在概念选择、追问、原页导航、练习和重答之间保持一致。
4. 正确判定学生答案，并给出相关解释和适当提示。
5. 在可记录的延迟与资源开销下完成上述任务。

采用固定测试集离线评测及固定交互脚本。结果用于说明系统可靠性、导航正确性、反馈质量与运行效率。模拟学生答案和脚本重答不能证明真实学习效果。

第一轮可从一份讲义的局部内容开始；最终扩展至 Proposal 计划的同一课程 2–3 份讲义。首轮建议选 warp 执行、延迟隐藏和分支发散；范围与来源按实际 PDF 物理页码记录。

## 2. 测试集构建

### 2.1 最终规模与首轮起点

沿用 kickoff 的大致总体目标：约 20 个概念、15 条显式关系、20 个讲义问答、10 道练习、20 份典型错答、8 个交互任务。此外补充正确作答及证据不足问题，防止只检查错误答案。

建议首轮先用 6–8 个概念、8–10 条关系、6 个可回答问题、4 个证据不足问题、2 道练习及其正确/错误答案、4 条交互脚本。首先让流程可跑，再扩充数量。数量不是 Proposal 规定的硬指标。

练习覆盖选择、判断、数值、开放题，按系统实际支持情况分批加入；未实现的题型标为未覆盖，不声称已经评测。

### 2.2 人工参考数据

每个概念保存：ID、名称、可接受别名、定义要点、原文证据及页码。

每条关系保存：起点、终点、关系类型、方向、来源、是否推断。主要参考集优先选讲义明确说明或图示直接支持的关系。

每个问答保存：问题、目标概念、必要答案要点、可接受证据页、是否可由所选讲义回答。

每道练习保存：题型、题干及条件、标准答案、评分规则、模拟学生答案及人工判定。题目来源标记为讲义复用、人工自编或模型辅助。

模型可辅助整理候选材料，但参考答案和来源由成员核对，另一名成员复核。AI 生成的参考答案不能直接当作真实标准。

### 2.3 开发集与保留集

开发集用于反复测试、查错和优化；保留集在冻结系统后用于最终检验。建议约 70% 开发、30% 保留，按题目家族分组，而非随意拆分答案条目。

同一题的不同错答、正确答案、同义改写和近似代码变式进入同一组。保留集标注、标准提示和预期错因不得进入模型上下文或检索库。

讲义本身属于可用知识源，不需要隐藏；需要隐藏的是保留测试问题及其评审标签。概念参考集如果已被用于人工修订图谱，则相同节点上的结果属于开发验收，不能称为独立抽取测试。需要独立结论时，使用未按参考标签人工修订的讲义页段或文档。

### 2.4 运行数据与评审数据

运行输入包括问题、学生提交、必要对话上下文及实际允许使用的讲义和教学材料。评审数据包括逐样本期望判定、错误标签、评分记录和期望提示，仅供评分者使用。

题目通用评分规则是否提供给系统是实验配置的一部分，必须列明；不能把某份学生答案的人工结论直接提供给模型。

## 3. 知识与引用的可靠性

### 3.1 概念抽取

操作：固定讲义和抽取配置，运行抽取，保存原始结果，再与人工参考集对齐。先按别名合并同义概念，去除重复节点，不能靠重复生成提高覆盖率。

指标：

- 概念覆盖率 = 正确覆盖的参考概念数 / 参考概念总数。
- 概念有效率 = 定义正确且能由讲义支持的生成概念数 / 审核的生成概念总数。
- 分别记录错误定义、遗漏和重复节点。

参考集未必列出所有合法概念，新增概念需审核后判定，不因不在参考集中就自动判错。

若图谱完全由 C 人工编写，该项评测的是图谱内容质量，不报告为模型自动抽取能力。

### 3.2 关系正确性

逐条检查端点、方向、关系类型与证据是否一致；仅连接到两个正确概念不代表关系正确。

指标：

- 关系覆盖率 = 正确覆盖的参考关系数 / 参考关系总数。
- 关系正确率 = 正确的生成关系数 / 审核的生成关系总数。
- 单独记录未标记的推断关系、方向颠倒、类型错误和无证据关系。

主指标对讲义显式关系计算；推断关系另外评价合理性及标记准确性，不能冒充原文陈述。不同措辞但含义等价的关系可匹配，匹配规则由两名成员复核。

### 3.3 问答内容与引用

输入固定讲义问题，保留检索片段、回答和引用。答案按必要要点评 0–2 分：0=核心错误；1=部分正确但缺重要内容；2=要点完整且无实质错误。

引用检查分三层：

1. 存在性：文档、页码、片段有效，且相互对应。自动检查。
2. 支持性：引用是否真正支持对应关键主张。人工检查。
3. 覆盖性：需要讲义证据的关键主张是否都有支持性引用。人工检查。

分别统计有效引用数/输出引用数、支持性引用数/审核引用数、有支持性引用的关键主张数/需证据的关键主张数。无引用时不将前两项记为 100%，记录不适用并通过覆盖率体现缺失。

同一主张重复贴多个引用不能扩大主张覆盖数。样本少时检查全部输出；规模扩大后提前固定抽样方法和数量，双方使用相同样本，不能看完结果再挑好例子。

### 3.4 证据不足与合理回答边界

测试两类问题：所选讲义有充分依据的问题，以及讲义没有足够依据的问题。后者可涉及未讲过的硬件规格或没有提供数据的精确性能预测。

人工先核对整份允许检索的材料，不能因为检索没找到就把问题标为超范围。

记录：

- 证据不足识别率：在不足样本上明确说明限制、且未伪装成有讲义依据回答的比例。
- 不必要拒答率：可回答样本中错误拒答的比例。
- 虚构引用及把外部知识冒充讲义结论的案例。

允许提出澄清问题或给出明确标记的补充说明；重点是依据和结论的边界诚实、清楚。

## 4. 概念图导航与多轮任务

这是 StudyGraph 功能验收，主要由 A 实现自动测试，B 提供日志，C 核对语义。Baseline 不具备图谱界面时，不因缺少该界面扣输出质量分。

### 4.1 八条固定任务建议

- N01 选择概念后问“解释这个概念”：请求包含正确 concept_id，回答围绕该概念。
- N02 直接提问：未选节点也能检索回答，不错误沿用旧概念。
- N03 连续追问“为什么”“举个例子”：保持当前主题及相关证据。
- N04 从概念 A 切到 B：后续解释按新选择执行，不串用旧主题。
- N05 点击回答引用：打开正确文档和 PDF 物理页，不能只验证页码而忽略文档。
- N06 请求与当前概念相关的练习：题目实际内容与目标概念一致。
- N07 答错、请求提示、重答：保留两次不同 attempt、同一题和会话关联，以及提示事件。
- N08 检索无结果或模拟请求失败：显示明确状态，可重试；不留下虚假的成功记录或错误引用。

每条脚本写明初始状态、操作序列、预期结果、检查点和超时。脚本前重置或创建独立会话，避免历史污染。

### 4.2 指标

- 上下文对齐率：语义上符合当前任务上下文的回应数 / 检查的回应数。
- 引用跳转成功率：正确打开文档与原页的次数 / 跳转尝试数。
- 多轮任务完成率：所有必需检查点均通过的脚本数 / 执行脚本总数。
- 作答记录完整率：按要求完整保存的学习事件数 / 应保存事件数。

ID、页面状态和数据库记录适合自动断言；答案和题目是否真正相关需要人工核对。若使用模型自动评分，应先人工校准并报告限制，不把字段相同当作语义正确。

按脚本报告失败位置，不能用多个成功点击掩盖一个完整任务失败。脚本给出的正确重答只验证流程，不视为提示改善学习的证据。

## 5. 反馈质量与系统效率

### 5.1 判分、反馈与提示质量

详细题型处理、评分尺度和示例见配套文档：[不同题型的判分与系统评测](不同题型的判分与系统评测.md)。

执行要点：

- 固定题目、学生提交和评分规则，跳过出题环节，检查批改与反馈。
- 选择/判断题优先规则判分，数值题检查误差与单位，开放题按必要要点评价。
- 只有选项时评判定、解释、提示和引用，不要求精确推断学生内在错因。
- 选项加理由或开放题，再评价错因定位。
- 正确、部分正确和错误答案都覆盖；不适用的维度不记为 0。

每条输出分别报告判定、技术正确性、针对性、提示可行动性及引用，避免不透明总分掩盖技术错误。

### 5.2 动态出题质量：补充评测

系统若支持现场生成题目，需补测该环节。固定讲义、概念、题型与难度要求，多次生成；允许题目不同，不使用完全相同文本作为成功标准。

人工检查范围相关性、题意与条件是否充分、可解性、标准答案正确性、评分依据一致性及来源支持。单选题检查唯一正确选项；判断题避免条件缺失造成真假不确定。

记录各项通过率及严重失败案例。动态生成题目质量与固定题反馈质量分开报告，避免把坏题导致的反馈失败全部归因于批改模型。先完成核心评测，再按实际功能加入此项。

### 5.3 系统效率

记录整体请求耗时、检索阶段耗时、全部模型调用耗时与次数、输入/输出 token（接口提供时）、超时与失败。

计时口径：后端耗时从收到请求到完成响应；若测用户可见耗时，则另从前端提交到展示完整结果。流式首字时间可单列，不能替代完整响应耗时。

记录并行阶段及实际时间戳，不能把并行调用时长简单相加当作总墙钟时间。工具调用、重试和额外模型步骤均计入所属系统整体开销。

报告样本数、中位数和范围；样本足够时再提供尾部百分位。冷启动与预热分开，缓存策略、并发数和超时统一。失败/超时另报比例及实际等待，不从结果中无声删除。

## 6. Baseline、实验配置与结论范围

### 6.1 主对照

Baseline：使用相同 TACC 模型和讲义检索组件，直接生成答案、解释或反馈。

StudyGraph：在该基础上使用已实现的概念关联、针对性反馈和学习状态等能力。列出实际启用模块，不将计划功能当作已实现功能。

共同条件：讲义及版本、解析和基础检索配置、模型版本、用户问题、学生提交、必要对话历史、任务要求和生成预算。两者都允许解释和给提示，不能通过刻意削弱 baseline 制造提升。

双方规则判分使用同一标准答案。用于语义诊断的通用 rubric 是否共同可见必须记录：

- 主系统对照：若仅 StudyGraph 使用 rubric、概念图等，则结论属于整套方案。
- 可选控制实验：双方共享 rubric，仅比较其他流程差异。

不同输入口径的结果分别汇总。若概念扩展导致证据不同，保存双方实际上下文；这属于系统差异，不能声称证据完全相同。

### 6.2 哪些项目配对比较

在同一问答和反馈输入上，比较答案正确性、引用支持、错因定位、反馈相关性及耗时。

概念抽取和关系质量主要是知识组织验收；图谱导航主要是 StudyGraph 功能验收。没有相应 baseline 功能时，不编造横向分数。

如需证明概念图的独立贡献，可增加“移除概念关系、其余保持相同”的消融。整体提升不能直接归因为某一个工具。

### 6.3 运行与人工评分

- 每个输入配对运行两个配置，交替或随机运行顺序。
- 首轮每输入一次排除运行问题；正式比较建议每输入各 3 次，保存全部结果。次数在开跑前确定。
- 系统输出匿名编号，评分者不看系统标签。两名成员按同一规则独立评分，保存分歧及裁定。
- 对同一 case 计算差值，再汇总平均差值、胜/平/负及失败数。不同题型分开报告，不让题量多的类型掩盖其他类型。
- 同题重复、同题不同错答并非完全独立题目，报告题目数和提交数；小样本以描述结果为主，不轻率声称统计显著。

## 7. 从第一版后端到最终报告

1. C 准备少量公开开发样例、参考证据和评分规则；A、B 交叉复核。
2. B 先跑通讲义检索、回答/反馈和日志；A 跑通概念及引用入口。不要求先实现所有 Agent 工具。
3. C 评价实际输出，按“输入、失败输出、违反的标准、证据”记录问题。
4. 团队选定优先问题改进，同样开发输入再次运行，保留前后版本结果。
5. 扩充到最终讲义范围和题型；补齐导航与效率记录。
6. 冻结代码 commit、prompt、模型、检索配置、数据版本和指标，运行保留集。
7. 汇总结果与至少一个失败案例，区分已覆盖、未实现和未验证的内容。

如果根据保留集结果继续优化，原测试集转为已见数据；需要新的独立样本才能再次做未见测试声明。

## 8. 数据记录与报告结构

每次运行至少保存 run_id、case_id、split、任务类型、system/config、代码及数据版本、原始输入、实际检索片段、模型原始输出、结构化输出、引用、时延、失败状态和评分者记录。凭据不进入日志或仓库。

最终报告建议包含：

1. 数据范围、题型、题量、开发/保留划分及人工核对方法。
2. 两套系统实际配置与输入差异。
3. 知识与关系质量。
4. 问答、引用与证据不足结果。
5. 导航及多轮完成情况。
6. 分题型反馈结果与效率成本。
7. 失败案例、未覆盖范围及结论边界。

不预填未测分数或虚构提升比例。规则正确性、模型质量和交互成功率分项展示，不混成一个没有解释的总成绩。

## 9. 责任与开始测试前的确认

- A：交互脚本、概念上下文、引用跳页及前端状态验收。
- B：模型/检索与配置、批量运行、日志及性能计时。
- C：参考知识、题目与模拟答案、评分细则、结果汇总。
- 共同：来源复核、盲评、保留集执行及失败分析。

开始正式测试前确认：最终讲义、样本量与划分、实际支持题型、baseline 输入口径、模型/预算、重复次数、超时设置、评分者与冻结版本。

本文依据项目 Proposal 的 Evaluation Plan 和团队 kickoff 分工制定；具体数字与实施方式属于本方案建议，不作为 Proposal 原文引用。

## 切换 TACC / DeepSeek 运行评测

以下是当前代码的运行方式，历史报告中的模型名称和成绩保持原样；切换模型后应保存到新的结果目录并重新评分。[完整配置、参数和运行说明](../../evaluation/runners/README.md)。命令均从仓库根目录执行。

先启动 TACC 模型及 SSH 隧道，然后在运行评测脚本的终端设置地址并检查接口：

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1

curl --noproxy '*' -fsS --max-time 8 \
  http://127.0.0.1:18024/v1/models
```

直接调用 TACC 的评测脚本不需要 DeepSeek API key。改用 DeepSeek 时，需要在当前进程配置 `DEEPSEEK_API_KEY`。如果密钥已保存在项目 `.env` 中，可以加载：

```bash
set -a
source .env
set +a
```

按评测角色选择以下命令。所有命令均使用项目的 `.venv/bin/python`，输出路径需尚未存在。

**1. TACC 出题，并使用 TACC 评分**

```bash
.venv/bin/python -m evaluation.runners.quiz \
  --provider tacc \
  --output-dir evaluation/results/quiz-tacc-new
```

如果希望由 TACC 出题、DeepSeek 担任裁判：

```bash
.venv/bin/python -m evaluation.runners.quiz \
  --provider tacc \
  --judge-provider deepseek \
  --output-dir evaluation/results/quiz-tacc-deepseek-new
```

**2. TACC 批改学生答案**

```bash
.venv/bin/python -m evaluation.runners.grading_feedback \
```

**4. 概念图生成与 AI tutor：切换后端模型**

在后端终端中加载配置后，设置模型并启动后端。示例端口 `18031` 必须空闲；若后端已经运行，需要停止旧进程后重新启动，或选择另一个空闲端口。

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1
export STUDYGRAPH_GENERATION_PROVIDER=tacc
export STUDYGRAPH_TUTOR_PROVIDER=tacc

.venv/bin/python -m uvicorn backend.main:app \
  --host 127.0.0.1 \
  --port 18031
```

在另一终端运行 HTTP 评测时，将 `--base-url` 指向这个后端，例如：

```bash
.venv/bin/python -m evaluation.runners.tutor_single run en \
  evaluation/results/tutor-single-tacc-new \
  --base-url http://127.0.0.1:18031 \
  --job CURRENT_JOB_ID
```

将 `CURRENT_JOB_ID` 替换为实际 TACC 作业号，并确保两份讲义已导入该后端。此命令生成回答，语义评分仍需另行审核。

切回 DeepSeek 时，将相应命令参数中的 `tacc` 改为 `deepseek`。对于 HTTP 评测，要修改后端终端中的配置并重启后端：

```bash
export STUDYGRAPH_GENERATION_PROVIDER=deepseek
export STUDYGRAPH_TUTOR_PROVIDER=deepseek
```

题集校验、页码覆盖检查、基于保存评分的汇总不调用模型，无需切换。
