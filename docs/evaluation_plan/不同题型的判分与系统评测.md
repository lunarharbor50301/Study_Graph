# 不同题型的判分与系统评测

版本：v0.1，2026-11-10。用途：团队讨论与评测设计；本文没有实测结果。

## 1. 先区分两种评分

**系统给学生判分**：判断学生提交的答案是否正确，并按需要提供解释、提示。

**评测者给系统评分**：C 使用人工核对的标准答案和评分规则，检查系统是否判对、解释是否正确、提示是否合适、引用是否可靠。

提前准备标准答案，是为了明确正确性依据。真实学生提交的答案仍然未知；开发测试则用预先编写的模拟答案检查系统表现。

## 2. 不同题型采用不同判分方法

### 2.1 选择题与判断题

后端根据可信的标准答案进行规则比对，通常不需要模型参与判定。

例如，单选题标准答案为 B，提交 A 则判错，提交 B 则判对。判断题同理。多选题需要事先约定完全匹配还是允许部分得分，不能由模型临时决定。

规则还需处理合法选项、未作答、重复提交等情况。无效输入应明确返回输入问题，不应悄悄转换成普通错答。

AI 可以在规则判分后生成解释或提示；后端的判定结果与模型解释必须一致。

### 2.2 数值题

优先用规则检查数值、允许误差、单位和等价表达。例如 100 与 100.0 通常可视为相同；是否接受未写单位应由题目要求决定。

若要求展示推导过程，则将“最终数值是否正确”和“过程是否合理”分别评价。只比对结果不能判断学生的推理是否正确。

### 2.3 简答题与代码分析题

需要根据必要得分点判断含义，接受合理的同义表达，并区分结论与理由。模型可以辅助语义判断和错因分析。

例如，“不能消除发散，因为原 warp 内线程仍走不同路径”和“不能，因为 GPU 一次只能执行一个线程”结论相同，但后者理由错误，不能得到相同评价。

开放题可以用固定题目、模拟学生答案和人工参考要点开展开发测试。这不是所有题型都必须执行的统一 AI 判分流程；整体安排见[总体评测方案](总体评测方案.md)。

## 3. 选择题、判断题如何评价系统

### 3.1 判定正确性

检查系统判定是否与人工核对的标准答案及计分规则一致。

判定准确率 = 判定正确的有效提交次数 / 有效提交总次数。

正确答案和错误答案都要测试，避免只测试错答而漏掉“把正确答案判错”的情况。固定答案的规则比对通常应全部通过；这一项主要是功能验收，不足以体现 AI 的反馈能力。

无效输入另报输入校验结果；超时或运行失败另报失败率，不悄悄丢弃，也不当成普通学生错答。

### 3.2 解释正确性：0–2 分

- 0 分：存在实质性知识错误，或解释与判定结果矛盾。
- 1 分：结论正确，但只重复“选错了/选对了”，缺少题目要求的关键理由。
- 2 分：解释正确、与题目相关，并说明关键原因。

对正确答案，确认并简要说明依据即可，不要求强行制造错误或纠错提示。文字长度不是评分依据。

### 3.3 提示相关性与可行动性：0–2 分

仅在该测试请求提示时计分：

- 0 分：提示错误、无关，或把学生引向错误方向。
- 1 分：方向大致相关，但只说“再看看讲义”等笼统建议。
- 2 分：针对当前题目，给出明确的观察或推理下一步。

请求提示时，另记录是否过早给出完整推理答案；用户明确请求完整解释时，不因直接解释而扣分。若产品已经展示正确选项，提示仍可保留推理过程，不要求重新隐藏已展示的信息。

### 3.4 引用可靠性

分别检查：

1. 引用是否有效：文档、页码、片段是否存在且能打开。
2. 引用是否支持解释：原文是否真正支持对应主张。
3. 关键解释是否缺证据：不能仅引用一个次要事实就认定整段解释有依据。

可以记录支持性引用数 / 审核引用数；无引用时不计作 100%，并记录关键解释缺证据。页码可打开不代表语义支持。

### 3.5 诊断是否有充分依据

只看到错误选项，通常不足以确定学生的真实错因。学生可能猜测、误读或有不同误解。

允许说“这个选项可能把……混淆了”或追问理由；不应无依据地断言“你一定不理解某概念”。即使选项按典型误解设计，也只能支持诊断假设。

记录无依据的确定性诊断次数。对“只有选项”的样本，不把精确错因定位设为必得分项。

## 4. 示例：一道判断题的测试

### 4.1 题目与标准答案

题干：在不改变原 warp 内线程的数据分配、分支条件和代码时，只增加启动的线程数量，就能消除原 warp 内的分支发散。

标准答案：错误。

依据：增加其他线程不会直接改变原 warp 内的路径分布。其他就绪 warp 的调度可以帮助隐藏等待，但不等于消除原 warp 的分支发散。

来源：`lecture_sample.pdf`，PDF 物理页码 p.37、p.41、p.44–45。使用前需按实际解析结果绑定真实文档和片段 ID。

### 4.2 学生选“正确”，没有说明理由

系统应判错。合适的反馈示例：

> 这个判断不正确。增加线程数量没有改变原 warp 内各线程的分支条件。你可以先只观察原来的一个 warp：执行某条路径时，另一条路径上的线程是否在做有效工作？

评测者检查判定、解释、提示与引用，不要求系统准确猜出学生为何选错。

不合适的诊断示例：

> 你一定把延迟隐藏和分支发散混淆了。

仅凭该选项无法确定这一错因。

### 4.3 学生选“错误”，没有说明理由

系统应判对，可以简要解释依据，或邀请学生进一步解释。不能因为没有提交题目未要求的理由就判错，也不能由一次选对推断其完全掌握概念。

### 4.4 学生选“正确”，并提供错误理由

学生理由：“其他 warp 可以把空闲资源填满，所以原 warp 的发散就消失了。”

此时有依据检查系统是否识别“其他 warp 的调度”和“原 warp 内分支情况”的混淆。

错因定位评分：0=错判或只说错误；1=发现部分问题但含糊；2=准确指出理由中的混淆，并说明区别。

### 4.5 学生选“错误”，但理由错误

学生理由：“因为 GPU 一次只能运行一个线程。”

系统应区分两个结论：选择正确，理由错误。建议输出 answer_correct=true、reasoning_correct=false，避免把整个答案笼统判为完全正确。

如果产品只要求选择，理由评价应作为附加反馈；如果题目明确要求“选择并解释”，则按预先规定的选择分和理由分计分。

## 5. 选择题的补充设计

选择题可用同样方法测试。单选题建议覆盖正确选项及每个主要干扰选项，检查解释是否对应当前选择，而不是对所有错误选项返回同一段话。

题目作者可记录每个干扰项的设计意图，帮助生成相关解释。但“选了某干扰项”不等于已经证实学生具有该误解；需要学生理由或后续追问才能作更确定的诊断。

多选题提前确定漏选、错选、顺序及部分得分规则，并检查后端一致执行。不要把选项排列不同误判为答案不同。

## 6. 动态生成题目的标准答案也需要检查

AI 生成的标准答案可能错误。后端正确比对了一个错误答案，仍然会给学生错误反馈。

因此区分两种评测：

- 固定题批改评测：使用人工核对的题目与答案，测判分和反馈。
- 动态出题评测：检查生成题目是否清楚、单选题是否只有一个正确选项、标准答案是否正确、评分依据是否与题目一致、出处是否支持。

两者分别报告，方便定位问题来自出题还是后续反馈。

## 7. Baseline 与 StudyGraph 怎样比较

固定选择题和判断题使用相同标准答案、计分规则和后端规则判定。两者判定准确率可能相同，这符合预期。

若比较 AI 反馈，两者都获得同一题目、学生选择、规则判定结果、相同任务要求和讲义检索条件；有学生理由时，两者都获得该理由。记录概念关系、评分依据和学习记录等额外输入的差异。

重点比较解释正确性、提示相关性、引用支持、无依据诊断，以及端到端耗时。只有在输入包含理由时，再比较错因定位质量。

若产品仅返回“对/错”，没有解释和提示功能，则做规则和接口验收，不凭相同的规则比对结果宣称 StudyGraph 的 AI 更优。

## 8. 首轮执行与记录

1. C 准备一道人工核对的题目，列出正确选项、错误选项及可选的学生理由。
2. B 使用同一规则判分，生成配置对应的解释或提示，保留原始输出及引用。
3. C 按适用维度评分，注明“不适用”的项，不将其计为 0 分。
4. 根据具体失败样例修改系统，再用相同输入复测。另留新题进行最终测试。

每条记录至少包括：case_id、题型、题目版本、学生选择、可选理由、标准选择、规则判定、系统解释、提示、引用、各维度评分、耗时和失败状态。

选择是否正确、理由是否正确、反馈是否正确分别记录。它们评价的是不同对象，不宜混成一个无法解释的总分。

## 9. 团队分工

- C：核对题目与标准答案，编写模拟提交和评分规则，检查反馈与证据。
- B：实现规则判分、反馈生成、引用绑定及测试日志；根据具体失败案例改进。
- A：展示选择判定、解释和提示，支持按设计收集理由与重试。

配套总方案：[总体评测方案](总体评测方案.md)。两个文件放在同一目录即可相互引用，无需依赖其他开发文档。

## 切换 TACC / DeepSeek 运行评测

以下是当前代码的运行方式，历史报告中的模型名称和成绩保持原样；切换模型后应保存到新的结果目录并重新评分。[完整配置、参数和运行说明](../../evaluation/runners/README.md)。命令均从仓库根目录执行。

先启动 TACC 模型及 SSH 隧道，然后在运行评测脚本的终端设置地址并检查接口：

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1

curl --noproxy '*' -fsS --max-time 8 \
  http://127.0.0.1:18024/v1/models
```

直接调用 TACC 的评测脚本不需要 DeepSeek API key。改用 DeepSeek 时，需要在当前进程配置 `DEEPSEEK_API_KEY`。如果密钥已保存在项目 `.env` 中，可以加载：

```bash
set -a
source .env
set +a
```

按评测角色选择以下命令。所有命令均使用项目的 `.venv/bin/python`，输出路径需尚未存在。

**1. TACC 出题，并使用 TACC 评分**

```bash
.venv/bin/python -m evaluation.runners.quiz \
  --provider tacc \
  --output-dir evaluation/results/quiz-tacc-new
```

如果希望由 TACC 出题、DeepSeek 担任裁判：

```bash
.venv/bin/python -m evaluation.runners.quiz \
  --provider tacc \
  --judge-provider deepseek \
  --output-dir evaluation/results/quiz-tacc-deepseek-new
```

**2. TACC 批改学生答案**

```bash
.venv/bin/python -m evaluation.runners.grading_feedback \
  --provider tacc \
  --workers 1 \
  --output-dir evaluation/results/grading-tacc-new
```

**3. TACC 对已有概念图进行语义评分**

以下以 Lecture 1 的现有预测为例，只重新评分，不重新生成概念图：

```bash
.venv/bin/python -m evaluation.runners.knowledge score \
  --reference evaluation/01_knowledge/v0.5-en/lecture1.json \
  --prediction evaluation/results/v0.5-en-20261119/l1/prediction.json \
  --judge tacc \
  --output evaluation/results/l1-tacc-metrics-new.json
```

**4. 概念图生成与 AI tutor：切换后端模型**

在后端终端中加载配置后，设置模型并启动后端。示例端口 `18031` 必须空闲；若后端已经运行，需要停止旧进程后重新启动，或选择另一个空闲端口。

```bash
export QWEN_BASE_URL=http://127.0.0.1:18024/v1
export STUDYGRAPH_GENERATION_PROVIDER=tacc
export STUDYGRAPH_TUTOR_PROVIDER=tacc

.venv/bin/python -m uvicorn backend.main:app \
  --host 127.0.0.1 \
  --port 18031
```

在另一终端运行 HTTP 评测时，将 `--base-url` 指向这个后端，例如：

```bash
.venv/bin/python -m evaluation.runners.tutor_single run en \
  evaluation/results/tutor-single-tacc-new \
  --base-url http://127.0.0.1:18031 \
  --job CURRENT_JOB_ID
```

将 `CURRENT_JOB_ID` 替换为实际 TACC 作业号，并确保两份讲义已导入该后端。此命令生成回答，语义评分仍需另行审核。

切回 DeepSeek 时，将相应命令参数中的 `tacc` 改为 `deepseek`。对于 HTTP 评测，要修改后端终端中的配置并重启后端：

```bash
export STUDYGRAPH_GENERATION_PROVIDER=deepseek
export STUDYGRAPH_TUTOR_PROVIDER=deepseek
```

题集校验、页码覆盖检查、基于保存评分的汇总不调用模型，无需切换。
